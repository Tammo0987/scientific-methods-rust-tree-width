\begin{abstract}
	Treewidth is a graph-theoretic measure of structural complexity with direct applications in compiler optimisation.
	Thorup~(1998) showed that the control-flow graphs~(CFGs) of goto-free C programs have treewidth at most~6, enabling efficient register allocation.
	Gustedt, M{\ae}hle, and Telle~(2002) extended this result to label-free Java and confirmed it empirically on the Java standard library, finding an average treewidth of~2.7 and a maximum of~5.
	In this paper, we perform an analogous empirical study for Rust.
	Rather than analysing the source language, we operate on Rust's Mid-level Intermediate Representation~(MIR), the compiler's own explicit CFG-based representation at which flow-sensitive analyses such as borrow checking are performed.
	We extract CFGs for all functions in the Rust standard library using a custom compiler driver and compute their treewidth with \texttt{FlowCutter}.

\section*{AI Statement}

AI tools were used at several stages of this project, as described below.

\paragraph{Literature discovery.}
AI assistants were used to support the literature search, particularly when relevant terminology was not known in advance.
Suggested papers and authors were followed up and verified independently using standard academic search tools.

\paragraph{Writing and structuring.}
AI tools were used as part of an iterative writing process.
Drafts of sections were refined in collaboration with AI assistants, which helped with structuring arguments, improving formulations, and maintaining a consistent academic tone.
In all cases, the content, reasoning, and decisions remained with the authors; AI suggestions were critically reviewed and frequently revised or rejected.

\paragraph{Consistency, grammar, and style.}
AI tools were used to check for grammatical errors, inconsistent terminology, and stylistic issues across the paper, including notation and sentence-level clarity.

\paragraph{Code generation.}
The implementation tooling for this project was produced through an iterative, AI-assisted process.
This was a two-directional process: AI tools proposed implementations that were reviewed and corrected by the authors, and authors proposed code that was reviewed by AI tools and subsequently revised by the authors.
