\section{Methodology}
\label{sec:methodology}

Our methodology consists of three stages.
First, we extract the CFG of each function by intercepting the Rust compiler pipeline after MIR optimisation.
Second, we compute the treewidth of each extracted CFG using \texttt{FlowCutter}~\cite{strasser_2017}.
Third, we aggregate the per-function treewidth values into a distribution and derive summary statistics.
The implementation used for this study is available as an archived Zenodo software release~\cite{repo}.

As established in Section~\ref{sec:rust-and-mir}, MIR is the representation at which the Rust compiler performs its own flow-sensitive analysis, making it the natural level at which to study the structural complexity of Rust programs.
We close the chapter by discussing our methodological choices and contextualising the approach relative to prior work.

\subsection{CFG Extraction from MIR}
\label{subsec:cfg-extraction}

CFGs are extracted using a custom \texttt{rustc} compiler driver (\texttt{mir-extractor}) that hooks into the compiler pipeline at the \texttt{after\_analysis} phase, at which point we use the optimised MIR for each function (see Section~\ref{sec:rust-and-mir}).

For each eligible function, it builds a simple undirected graph from the basic-block structure of the MIR body, normalises it, and serialises the result for downstream analysis.
We target the Rust standard library (\texttt{core}, \texttt{alloc}, \texttt{std}), compiled for the host platform, as a representative for real-world Rust code.
We analyse free functions and methods defined in \texttt{impl} blocks.
Because Rust supports generics, each concrete instantiation of a generic function is compiled to its own MIR body and treated as a separate function.
For example, a generic function \texttt{fn push<T>} gives rise to distinct entries for \texttt{Vec<u8>::push} and \texttt{Vec<String>::push}, each potentially with a different CFG.

Each MIR basic block becomes a node and each control-flow edge between blocks becomes an edge in the CFG.
Edges into \emph{cleanup blocks}, basic blocks only reachable via a Rust panic or unwind, are excluded, restricting the graph to normal execution paths.
This is analogous to the treatment in Gustedt et al., where Java exceptions are absent from the CFG representation by construction~\cite{gustedt_2002}.
Because treewidth is defined on simple undirected graphs, multi-edges are deduplicated and edges are treated as unordered pairs.
The intermediate result is then stored for further analysis.

\subsection{Treewidth Computation}
\label{subsec:treewidth-computation}

Treewidth is computed from the serialised CFGs using \texttt{FlowCutter}~\cite{strasser_2017}.
Across the standard library, this covers all 27,997 functions, processed in parallel with one solver per CPU core.
The computation is fully deterministic, ensuring that repeated runs on the same input produce identical results.

For each of the three groups (all functions, safe functions, and unsafe functions) we report the mean, median, and maximum treewidth, as well as the percentage of functions with treewidth at most 3 and at most 6.
The full distribution over treewidth values is reported for all functions combined, and the number of solver timeouts is tracked.

\subsection{Discussion}
\label{subsec:methodology-discussion}

Gustedt et al.\ are the closest prior work to ours, but the two studies answer subtly different questions~\cite{gustedt_2002}.
Following Thorup, Gustedt et al.\ ask: \emph{what does the structure of the programming language guarantee?}~\cite{thorup_1998}
We ask: \emph{what do real Rust programs actually look like, after the compiler has processed them?}
These are complementary, not competing, perspectives.

We measure the treewidth directly on optimised MIR CFGs.
Because optimised MIR reflects the code after MIR-level optimisations such as inlining and copy propagation, the graphs we analyse are considerably closer to what the program actually executes than a source-level representation would be, even if further optimisations still occur in the backend.
The approach is empirical: we measure what the treewidth of real Rust programs actually is, rather than what the language structure would theoretically bound it to.

A natural question is whether the borrow checker introduces structural complexity beyond pure control flow.
It does not: the borrow checker operates on a read-only view of the MIR and does not modify the CFG structure~\cite[Ch.~69]{rustc_dev_guide}.
Its annotations are removed before optimisation, and since we extract CFGs from \texttt{optimized\_mir}, borrow checker artefacts are absent from the graphs we measure.
The treewidth values we report therefore capture control-flow structure rather than borrow checking complexity.

The main limitation of this approach is that it is disconnected from Thorup's theoretical framework.
Thorup proved that goto-free C programs have treewidth at most~6 by constructing a decomposition from source structure, and Gustedt et al.\ extended this to label-free Java~\cite{thorup_1998,gustedt_2002}.
We cannot make an analogous formal claim for Rust at the MIR level, because lowering to MIR erases the source nesting that such a proof would rely on.
Our results characterise the distribution empirically, but do not explain from first principles why it must be so.
